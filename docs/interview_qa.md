**背：**

## 一、KV Cache 与 PagedAttention（必问区）

### Q1.1 ⭐⭐⭐ PagedAttention 解决什么问题？讲一下原理。

**背：**
"它解决 KV Cache 显存管理的问题。朴素做法是给每个请求按最大长度预分配连续显存，造成两类浪费：请求之间的大块**外碎片**，和预留而未用的**内部浪费**。PagedAttention 借鉴操作系统虚存的分页思想：KV 按固定块大小切分，每条序列维护一个 block table 做逻辑到物理的映射，按需分配。这样外部碎片归零，内部浪费降到每序列平均约半个块。代价是注意力计算要通过 block table 间接寻址，kernel 比 contiguous 访问复杂一些。"

**加分句**："我自己实现的时候把 slot 定义成 block_id×block_size+offset 的扁平行号，物理池就是 [layers, rows, heads, dim] 的张量，这样读写和并行切分都简单。"

### Q1.2 ⭐⭐⭐ 你的实现和 vLLM 有什么区别？为什么你不需要 copy-on-write？

**背：**
"vLLM v0 的块管理器支持子块粒度的共享：两个序列可以共享最后一个未满的块，谁要先往里写就触发 copy-on-write。我的实现和 vLLM v1 一样，**只缓存完整块**——部分块永远不进缓存树，所以匹配到的共享块都是不可变的完整块，序列永远写自己的私有块，**COW 就从系统中消失了**。代价是部分块的内容不复用，前缀命中粒度粗一些。我认为这个取舍非常划算：COW 的拷贝路径和引用计数是 v0 复杂度的主要来源，换来的那点命中率在多轮对话场景下很小。"

**加分句**："需要 COW 的场景其实是 beam search 和 n>1 的并行采样——fork 出来的序列共享前缀再分叉。我把 fork 列为扩展项，到时候可以按需加回 COW。"

### Q1.3 ⭐⭐ 前缀缓存的哈希怎么设计的？哈希碰撞怎么办？

**背：**
"每个完整块算一个 blake2b 内容哈希，关键是**链式**的：hash_i = blake2b(hash_{i-1}, 块 token)。这样前缀相同的序列整条哈希链都相同，匹配就是沿树走。碰撞方面，128 位 blake2b 在这个规模下碰撞概率可以忽略——工程上 vLLM/SGLang 也都不做碰撞校验。真正要小心的反而是**锁**：匹配到的块对运行中的序列加锁计数，只有锁为零的叶子才能被驱逐，否则运行中的序列会被抽掉 KV。"

### Q1.4 ⭐⭐ LRU 淘汰有什么问题？你怎么改进？

**背：**
"LRU 只看最近访问，不看两件事：这条前缀**重算有多贵**——一个 8K token 的 system prompt 被挤掉，重建成本远高于一条闲聊短前缀；以及它**再被请求的概率**。我的改进方向是把淘汰改成一个价值函数：期望复用概率 × 重算成本，再加一层准入控制，比如一次性出现的超长前缀直接不缓存，把内存让给热门前缀。我在项目里把淘汰做成了可插拔接口，内置了 LRU、LFU 和一个 cost-aware 基线，就是为了在这个插槽上做实验——这也是我最想做的论文方向。"

### Q1.5 ⭐ KV Cache 到底占多少显存？给个量级。

**背：**
"公式是 2×(K+V) × 层数 × KV 头数 × head_dim × 每 token 字节数。LLaMA-2-7B 是 2×32×32×128×2 字节 = **512KB/token**，4K 上下文一条序列就要 2GB fp16——比一个 batch 的激活大得多，所以 KV 才是并发的第一瓶颈。量化到 INT8 直接减半，这就是 KV 量化的价值。"

## 二、调度与 Serving

### Q2.1 ⭐⭐⭐ 什么是 continuous batching？收益从哪来？

**背：**
"传统静态 batching 要等整批所有序列都生成完才能换下一批，短请求被长请求拖死。Orca 提出 iteration 级调度：每生成一个 token 都重新组装 batch，完成的立即退出、新请求立即加入。收益主要来自 decode 阶段——decode 是访存受限的，batch 里多几个序列几乎不增加单步时延，但吞吐成倍涨。我的调度器每步做三件事：先给 decode 序列预留 slot，再让没做完的 chunked prefill 续块，最后按策略从 waiting 队列准入新请求。"

### Q2.2 ⭐⭐⭐ Chunked prefill 解决什么问题？

**背：**
"没有它的时候，一个 8K token 的大 prefill 会独占整个引擎一整步，这一步里所有正在 decode 的序列 TPOT 全部被拖爆。chunked prefill 把长 prompt 切成固定 token 预算的片，和 decode 序列**混在同一个 batch** 里跑——这可行是因为 vLLM v1 式的混批下 decode 只占预算里每个序列 1 个 token。效果是 TPOT 的尾部延迟显著变好，TTFT 只牺牲一点。我的调度器里 in-flight 的 prefill 分片优先续跑，防止饥饿。"

### Q2.3 ⭐⭐ 抢占怎么做？recompute 和 swap 怎么选？

**背：**
"内存不够分配新 token 的 slot 时就要抢占。两种模式我都实现了：**recompute** 把该序列的 KV 释放掉、整个上下文重新 prefill——看着浪费，但因为被释放的块会进前缀缓存树，重算时大概率直接命中，实际成本远低于首次；**swap** 把私有 KV 块拷到 host 内存，恢复时原样拷回，生成进度零丢失。选择标准是**重算成本 vs PCIe 拷贝成本**：输出长、prompt 短的负载偏 swap；prompt 长且前缀大概率还在缓存里时 recompute 反而便宜。vLLM v0 两种都有、v1 砍掉 swap 只留 recompute，我把两种都保留了，这样能实验对比。"

**加分句**："这里我踩过一个真 bug：被换出的序列溜进了普通准入路径，状态被重建污染——修完之后我把'换出序列只能经 swap-in 通道恢复'做成了调度器的不变量并用测试钉死。"

### Q2.4 ⭐⭐ Prefill 和 decode 的瓶颈为什么不同？

**背：**
"看算术强度。Prefill 一次处理 n 个 token，权重只读一次，FLOPs 是 2×参数量×n，算术强度正比于 n——4K tokens 就是几千 FLOP/byte，远超机器平衡点，所以是**计算受限**。Decode 每步只算 1 个 token，但权重和全部 KV 都要重新读一遍，8B 模型 16GB 权重在 A100 有效 1.4TB/s 下就是 10ms 左右，不管 batch 多大，所以是**访存受限**。这也是为什么 decode 的吞吐靠 batching 抬、prefill 的吞吐靠提高 SM 利用率抬，以及为什么 prefill 和 decode 对硬件配置的最优解不同——PD 分离的底层逻辑。"

### Q2.5 ⭐ TTFT 和 TPOT 怎么优化？说说手段。

**背：**
"TTFT 的手段：prefix caching 命中省 prefill、chunked prefill 防队头阻塞、PD 分离让 prefill 用计算型机器、预测性调度缩短排队。TPOT 的手段：continuous batching 提高 decode batch、CUDA Graph 消 launch 开销、大融合 kernel、TP 摊权重读、KV 量化减少每步读取、投机解码把多次前向合成一次。两边冲突的地方是资源：prefill 想要大算力小批，decode 想要大批高带宽——所以 SLO 指标我用 goodput，即同时满足 TTFT 和 TPOT SLO 的请求占比，这是 DistServe 提出的口径，比平均延迟诚实。"

## 三、张量并行（我写了完整实现，必被追问）

### Q3.1 ⭐⭐⭐ TP 的切分规则？为什么 attention 不需要通信？

**背：**
"按 Megatron 规则：QKV、gate、up 是**列并行**——权重按输出维切，每个 rank 算自己的头，无通信；o_proj、down_proj 是**行并行**——权重按输入维切，各 rank 输出部分和，做一次 all-reduce 求和；embedding 和 lm_head 是词表并行，前者 mask 掉不属于本 rank 的词 id 再 all-reduce，后者各算各的词表分片再 all-gather。注意力在头维度切分后**各头天然独立**，所以注意力本体零通信——每层总共就两次 all-reduce。我的实现里 TP=2、TP=4 的输出和单卡逐 token 一致，这是测试钉死的。"

**加分句**："GQA 有个约束：KV 头数要能被 TP 整除，比如 LLaMA-3-8B 是 8 个 KV 头，TP=2 每卡 4 个，TP=8 时每卡 1 个——我引擎构造时显式 assert。"

### Q3.2 ⭐⭐ TP=2 的时候 all-reduce 通信量多大？

**背：**
"ring all-reduce 的通信量是 2×(K-1)/K×消息大小，TP=2 就是 1×消息大小。消息大小 = hidden_size × 这一步的 token 数 × 2 字节。decode 时每步每序列只有 1 个 token，7B 模型 hidden 4096 的话单次 all-reduce 才 8KB——这么小的消息是**延迟受限**而不是带宽受限，所以 TP 对 decode 的通信优化重点是和计算 overlap、以及 NVLink 拓扑。这也是 TP 一般限制在节点内、跨节点用 PP 的原因。"

### Q3.3 ⭐ 你的 TP 是每个进程都跑调度器？和 vLLM 的架构差在哪？

**背：**
"我的是 SPMD：每个 rank 跑**完全相同的确定性调度器**，因为输入和随机种子一致，每步的调度决策天然相同，只有采样结果需要 rank0 广播给其他 rank。vLLM 是 driver + workers 分工：driver 跑调度，worker 只执行前向。SPMD 的好处是简单、不用序列化调度指令；代价是要求调度完全确定、不能有依赖本地状态的分支。我选 SPMD 是因为它是研究原型最快的正确路径，换成 driver/worker 只是工程重构，接口已经隔离好了。"

### Q3.4 ⭐ 你怎么验证 TP 写对了？

**背：**
"两条：一是**分片规则往返测试**——每个权重按规则切完再拼回去，必须和原始张量逐元素相等；二是**端到端一致性**——TP=2、TP=4 的生成输出和单卡逐 token 相同。另外我有两个通信后端：一个线程级的模拟后端让 TP 代码在 CI/无 GPU 机器上跑，一个真 torch.distributed 的 gloo 后端，实测双进程输出也和单卡一致。上 GPU 只需要把后端换 NCCL，接口零改动。"

## 四、投机解码（高频新热点）

### Q4.1 ⭐⭐⭐ 投机解码的原理？为什么输出和普通解码完全一样？

**背：**
"每轮 draft 模型快速提 k 个 token，target 模型把 [上一个 token + k 个 draft] 一次 teacher-force 前向，得到 k+1 个位置的目标分布；然后逐位验证：draft 的 token 和 target 的 argmax 一致就接受，第一个不一致的位置就采 target 自己的 token 作为纠正——所以每轮至少产出 1 个正确的 token，全对的话第 k+1 个就是免费奖励。温度大于零时用标准拒绝采样，接受概率是 min(1, p/q)，拒绝时从残差分布 norm(max(p-q,0)) 采样——可以证明最终输出分布严格等于 target 分布。greedy 是它的特例，输出逐 token 一致，这一点我写成了测试。"

### Q4.2 ⭐⭐ 加速从哪来？什么时候反而变慢？

**背：**
"加速来自**前向调用次数减少**：decode 是访存受限的，一次前向 5 个 token 和 1 个 token 的时延几乎一样，全接受时一轮就出 5 个 token。变慢的条件是接受率低——draft 每轮自己要跑 k 步，如果 draft 不够小或者和 target 分布差太远，这些成本就白花。经验上 draft 要比 target 小一到两个数量级、接受率 60-70% 以上才净赚。我还区分了两个指标：接受率和 target 前向调用摊销——我自己测试里自投机（draft=target）接受率 100%，16 个 token 只用了 4 次 target 前向。"

**加分句**："工程难点其实在于把投机解码融合进 continuous batching——batch 里每个序列接受数不同，需要动态重组成 verify batch，vLLM V1 的 spec-decode 就在做这个，我把它列为 roadmap。"

### Q4.3 ⭐ prompt lookup 是什么？

**背：**
"不用 draft 模型的提议器：拿 context 末尾的 n-gram 到前文里找匹配，把匹配位置的后续直接当提议。对重复性强的负载——代码编辑、RAG 引用、多轮改写——接受率很高，成本几乎为零。限制是它没有分布，只能做 greedy 验证，这点和 vLLM 的实现一致。"

## 五、量化

### Q5.1 ⭐⭐ KV Cache 怎么量化？粒度怎么选？

**背：**
"粒度从粗到细：per-tensor 一个 scale（vLLM 的 fp8 KV）、per-block、per-token、per-channel。K 和 V 的敏感度不一样——K 的异常值集中在固定的少数通道，所以 KIVI 对 K 用 per-channel、对 V 用 per-token。我的基线实现是 per-(row, head) 对称量化：一行是一个 token 一个 KV 头的向量，写时量化读时反量化，不需要跨行统计、也不用重校准，正确性最容易保证；更细的粒度需要在池子里给 K 加转置布局，我把它留作研究扩展——粒度×校准×旋转三者的权衡本身就可以做实验。"

### Q5.2 ⭐ AWQ、GPTQ、SmoothQuant 的区别？

**背：**
"先分两类：weight-only 和 weight+activation。**GPTQ** 是基于 OBQ 的逐层逐列量化，用 Hessian 信息补偿量化误差，通常配 group-wise scale，压到 3/4 bit；**AWQ** 观察到少数显著权重通道由激活幅度决定，按激活分布做 per-channel 缩放保护它们，不需要反传；这两个都是 weight-only，激活保持 fp16，适合单卡小 batch。**SmoothQuant** 是 W8A8——激活也量化成 INT8 才能吃到 INT8 GEMM 的算力，它通过一个平滑变换把激活的异常值迁移到权重里，让两边都好量化。我的项目里实现的是 W8A8 的数值参考，CUDA 上应该换 torch._int_mm 或 CUTLASS kernel。"

## 六、模拟器与研究

### Q6.1 ⭐⭐ 你的模拟器怎么建模单步时间？结果可信吗？

**背：**
"用 roofline 式解析模型：单步时间 = max(FLOPs/有效算力, Bytes/有效带宽) + launch 开销，FLOPs 是 2×参数量×(prefill token 数 + decode 序列数)，bytes 是权重加全量 KV。有效常数用的是实测可达值而不是 datasheet 峰值。可信度我说实话：**未校准前是趋势工具不是精确预测器**——所以我写了校准模块，从真实测量里拟合三个常数，报告 MAPE。我的计划就是在 4090/5090 上跑 benchmark_serving 拿实测数据喂它，模拟器和实机的 gap 校准本身就能发一篇 benchmark 短文。"

**加分句**："模拟器有个设计点我很满意：前缀缓存用的 RadixCache 类和真实引擎是**同一个类**，策略代码在两边行为完全一致，避免'模拟器里调好的策略到实机失效'。"

### Q6.2 ⭐ 路由策略你比出什么结论了？

**背：**
"合成负载下的结论：prefix-affinity 靠前缀哈希把相同会话粘在同一副本，命中率最高，但 Jain 公平指数会掉——负载不均；least-loaded 均衡性最好但命中率低；predictive 路由把预测的工作量和前缀亲和加权融合，是两者的折中。我的模拟器里这些是一键对比的：一个 `--compare-routers` 出一张表，固定 seed 可复现。真实 trace 上的结论要等接上 Azure/BurstGPT 数据跑完才能下，这正是我论文的实验计划。"

## 七、调试与工程（展现工程素养）

### Q7.1 ⭐⭐ 讲一个你调试过的最难的 bug。

**背（选一个讲，推荐 #9）：**
"我在写投机解码时，先独立写了一个非分页的参考实现来和主引擎交叉验证，两边 prefill 的 logits 差了 6e-4——量级看起来不大，但生成第二个 token 就发散了。逐层对拍发现差异从第 0 层就存在，最后定位到 KV 池的一个真 bug：dtype 设成 auto 的时候，量化器被硬编码成 fp16，我 CPU 上 float32 模型的 KV 也被静默降成 fp16 存储，每次写读引入 2.4e-4 的舍入误差，逐层放大后 argmax 翻转。修复后两边 diff 降到 1e-7。这件事给我两个习惯：**新机制要有一套独立实现做交叉验证**，以及数值 bug 用'逐层 diff'比看代码快得多——当时的逐层对拍脚本我留在了仓库 scripts/debug 目录里。"

### Q7.2 ⭐ 讲讲测试策略。为什么测这么细？

**背：**
"62 个测试，但我最看重的是三类**一致性测试**：前缀缓存开和关、chunked prefill 开和关，四种组合输出必须逐 token 一致；TP=2/4 和单卡一致；投机解码和普通解码一致。这类测试的特点是**不依赖对'正确输出'的预设**——随机权重的小模型输出没人知道该是什么，但'同一模型不同路径输出必须相同'是数学事实，一测一个准。开发中这些测试抓过真 bug：decode 路径不更新已计算 token 数、swap 序列溜进普通准入路径污染状态，都是 e2e 一致性测试先红的。"

### Q7.3 ⭐ Python 写引擎，性能够吗？

**背：**
"不够，而且我是故意的。这个项目的定位是**研究测试台**：策略实验在模拟器里跑（纯 Python、秒级迭代），正确性在参考引擎里验证（可读性优先），性能数字由 Triton kernel bench 和真实框架对比补齐。参考实现慢的地方我有明确预期：注意力是逐序列 gather，production 应该用 FlashAttention 或我写的 Triton kernel；decode 应该上 CUDA Graph。我反而认为'每个性能点都知道该换成什么'是比'每个地方都快'更强的能力信号——我现在正在 GPU 机器上把 kernel bench 的数字补上。"

## 八、框架生态（证明你了解上游）

### Q8.1 ⭐⭐ vLLM v0 和 v1 的区别？

**背：**
"四个关键点：①调度——v0 prefill/decode 分批交替，v1 混批加 chunked prefill；②KV 管理——v0 有子块共享和 COW，v1 整块哈希匹配、无 COW；③前缀缓存——v1 默认开启；④执行——v1 更激进的 CUDA Graph 和多进程架构，调度进程与 worker 分离。我的项目在这几个分叉点上都有对应实现或开关，所以能逐条讲清取舍。"

### Q8.2 ⭐ SGLang 的 RadixAttention 和 vLLM 的 prefix caching 区别？

**背：**
"本质都是内容寻址的 KV 复用，数据结构不同：SGLang 用 radix 树，天然支持前缀的层次复用和 LRU 叶子驱逐，还配了 cache-aware 路由；vLLM v1 用哈希表映射块，实现更扁平。树的好处是'最长前缀匹配'语义清晰、驱逐有结构（叶子优先）；哈希表的好处是简单、每块独立。我实现的是树版，并且把驱逐策略做成了可插拔接口。另外 SGLang 的 zero-overhead 调度器把调度和执行 overlap 起来，这是它吞吐好的重要原因之一，我列为 roadmap。"
